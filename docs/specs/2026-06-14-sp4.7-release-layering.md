# SP4.7 — Release layering: bounded serving + per-app archive

> Sub-spec of SP4 (release automation). Addresses the SP4.7-#1 follow-up:
> the new pipeline collapsed the legacy per-app release channel into flat
> per-target blob buckets that grow without bound. This spec splits the two
> concerns the buckets conflate — **serving** the repo vs **archiving**
> versions — and makes the serving layer truly incremental.

**Status:** design approved 2026-06-14; §4 mechanism revised 2026-06-15 after a
container spike (see §4.1) proved the original "re-index in place" approach
infeasible and validated metadata-only merge instead. Pending implementation plan.

---

## 1. Problem

### 1.1 What the legacy did (two parallel channels)

- **Repos (apt/yum):** packages lived physically on `gh-pages`
  (`<dist>/<arch>/*.rpm` next to `repodata/`; apt `pool/` + `dists/`).
  `createrepo`/`apt-ftparchive` indexed them in place. This is what
  `dnf`/`apt` consumed.
- **Per-app GitHub Releases** (`node_exporter-v1.11.1`, …): a *separate*
  visibility/direct-download channel, one release per app per version. Not
  consumed by the repos. Each release was small (one version's artifacts) and
  individually prunable.

### 1.2 What the new pipeline does

- **Pages** holds only metadata (rpm `repodata`, `catalog.json`, GPG keys,
  dashboards) — ~5–15 MB, effectively constant.
- **Releases** hold the blobs, keyed by **repo coordinate**:
  `rpm-<target>-<arch>/*.rpm` (rpm repodata on Pages points here via
  createrepo `--location-prefix`) and `apt-<codename>/` (a **flat** apt repo —
  `Packages`/`Release` and the `.deb` side by side, no `pool/`, no `dists/`;
  see `forge/repo/deb.py`).
- **No per-app releases.**

### 1.3 The two defects

1. **Unbounded growth.** The publisher only does `gh release upload
   --clobber`. A new version has a new filename, so the old `.rpm` is never
   removed: each per-target bucket accumulates every version of every exporter
   forever. 300 bumps → 300+ assets piling into a single release, growing
   without retention. A release with thousands of assets degrades the UI/API.
2. **Serving is not actually incremental.** `build_rpm_repo` runs
   `createrepo_c` over the **physically staged** packages, which on an
   incremental run contain only the freshly-built item(s) (`rpm_groups` is fed
   by `_stage_artifacts` from `dist/` = built items only). `build_apt_repo`
   likewise rebuilds the pool from the current run's debs only. So a single-item
   run regenerates a repodata/`Packages` index listing **only that item** —
   dropping the other 33 from the index. The `FORGE_PUBLISHED_CATALOG_URL`
   merge fixes `catalog.json` but **not** the repo metadata. Today only
   `mode=all` (full rebuild) yields a complete repo.

### 1.4 Lost capability

The legacy per-app channel gave per-version visibility and manual downgrade
(`curl` the old rpm + `dnf install ./file.rpm`). The new model keeps the files
(by accident, in the flat bucket) but loses the clean per-version grouping.

## 2. Decisions (locked)

| Decision | Choice |
|---|---|
| Repo serves multiple versions of an item? | **No** — mono-version repo. The
repodata/`Packages` index the manifest-pinned version only (as legacy did).
Catalog model is **unchanged**. Downgrade is via the archive layer (direct
download), not via `dnf downgrade`. |
| Archive retention | **Keep the last 10 versions** per exporter (per-app
releases beyond the 10 most recent are deleted). |
| Serving layer location | **Releases** (per-target buckets), not Pages —
the current-version blob set across all targets is several GB, over the Pages
~1 GB soft limit. Pages stays metadata-only. |
| Full rebuild on every bump? | **No** — incremental strict, achieved by
**metadata-only merge** (§4): the index is updated by merging the changed item's
metadata into the published index. Unchanged blobs are never fetched, re-packaged,
re-signed, or re-uploaded. Per-run data transfer is the index (KB–MB), flat with
catalogue size — the cost does not grow with 34 → 100 → 1000 exporters. |

## 3. Target architecture: two layers

```
┌─ SERVING (what dnf/apt hit) — CURRENT VERSION ONLY, BOUNDED ───────────┐
│  Releases (blob CDN):                                                   │
│    rpm-el9-x86_64/   node_exporter-1.12.0…rpm  + 33 others (current)   │
│    rpm-el9-aarch64/  …                                                  │
│    apt-bookworm/     Packages + Release + current .deb (flat)          │
│  Pages: rpm repodata + catalog.json + GPG keys + dashboards (~10 MB)   │
│  Invariant: exactly one version per item per coordinate.               │
│  At bump: old version of the changed item is PRUNED from the bucket.   │
└────────────────────────────────────────────────────────────────────────┘
┌─ ARCHIVE (visibility + manual downgrade) — LAST 10 VERSIONS ──────────┐
│  Per-app Releases, one per version:                                    │
│    node_exporter-v1.12.0  → its rpm (all targets) + deb (all codenames)│
│    node_exporter-v1.11.1                                               │
│    … (≤10; older auto-deleted)                                         │
│  Each release small + individually prunable. Docker stays on GHCR/Hub. │
└────────────────────────────────────────────────────────────────────────┘
```

The current version's `.rpm` exists in two places (serving bucket + its
version's archive release). Duplication is intentional and free on Releases.

## 4. Mechanics: metadata-only merge

**The published index is the durable state, not the blobs.** A repo index is one
small *record* per package (name, version, size, checksum, download URL). A
record is a few KB of text; the blob it points at is ~10–20 MB. We generate a
package's record **once**, when it is built (the blob is on the runner). From
then on the serving index is maintained by **merging records** — the indexers
**never need the unchanged blobs again**.

This is the only approach that holds the per-run cost flat as the catalogue
grows: a re-index that needs all blobs present transfers gigabytes at 100+
exporters (§4.1); a record merge transfers only the index.

### 4.1 Why not "re-index in place" (spike, 2026-06-15)

The original §4 assumed `createrepo_c --update` could keep records for packages
whose `.rpm` is absent from the work dir. The man page and a container spike
disproved it: **`createrepo_c --update` drops any record whose file is not on
disk** — it describes exactly what it scans. `apt-ftparchive` rescans likewise.
So a complete index requires either all blobs present (the gigabyte transfer we
reject) or a record merge. The same spike validated the merge tooling:

- `mergerepo_c --method nvr --omit-baseurl` merges two repos **with zero `.rpm`
  files present** (exit 0), keeps the **highest version** of a duplicated package
  (mono-version for free), preserves a package present in only one input, and
  emits clean **absolute** `<location href="https://…/bucket/…rpm"/>` URLs.

### 4.2 RPM serving (per `rpm-<target>-<arch>` coordinate)

1. **Fetch** the published `repodata/` from Pages (KB–MB; not the blobs).
2. **Record** the freshly-built `.rpm`: `createrepo_c --location-prefix
   <bucket-url>` over a dir holding only that one file → a one-package repo.
3. **Merge**: `mergerepo_c --method nvr --omit-baseurl --repo <published>
   --repo <new-one-package>` → a complete index where the new version supersedes
   the old (NVR), every other record carried over verbatim with its absolute URL.
4. **Sign** `repomd.xml`; **push** the merged `repodata/` to Pages.
5. **Bucket delta**: upload the new `.rpm`; `gh release delete-asset` the
   superseded version. The other packages' blobs are untouched.

### 4.3 APT serving (per `apt-<codename>` coordinate, flat repo)

1. **Fetch** the published `Packages` text from the apt release (KB–MB).
2. **Record** the freshly-built `.deb`: `apt-ftparchive packages` over a dir
   holding only that one file → one control stanza.
3. **Merge**: drop every stanza whose `Package:` matches the changed item, append
   the new stanza (Debian control files are blank-line-separated records —
   carried-over stanzas keep their valid `Filename:`/checksums). Regenerate
   `Packages.gz`; run `apt-ftparchive release` over the merged `Packages*`
   (it hashes the index files, which are local — no `.deb` needed).
4. **Sign** → `InRelease` + `Release.gpg`; **push** the index to the apt release.
5. **Bucket delta**: upload the new `.deb`; `gh release delete-asset` the
   superseded version.

No upstream fetch, no nfpm, no re-signing of unchanged packages, no blob
re-download. Only the changed item's blob moves; only the index is rewritten.

### 4.4 Archive layer (independent)

For each built item: create/clobber the `{name}-v{version}` release with that
version's rpm (all targets) + deb (all codenames); then list `{name}-v*`
releases, sort by semver, and `gh release delete` everything beyond the 10 most
recent.

## 5. Code surface

| Component | Change |
|---|---|
| `forge/repo/rpm.py` | **New** `merge_rpm_repo`: record the one new `.rpm` (`createrepo_c --location-prefix`) then `mergerepo_c --method nvr --omit-baseurl` against the fetched published `repodata/`. Existing `build_rpm_repo` (full build) untouched — reused for `mode=all`/first publish. |
| `forge/repo/deb.py` | **New** `merge_apt_repo`: record the one new `.deb` (`apt-ftparchive packages`), splice its stanza into the fetched published `Packages` (drop old stanzas by `Package:`), regenerate `Packages.gz` + `Release`. Existing `build_apt_repo` untouched. |
| `forge/repo/published.py` | **New** fetcher for the published index (`repodata/` from Pages, `Packages` from the apt release) into a local work dir, reusing the SP1.4 `Downloader` seam. Returns `None` when nothing is published yet → caller falls back to a full `build_*_repo`. |
| `forge/repo/builder.py` | `build_distribution` gains a merge path: when a published index is available, per coordinate call `merge_*_repo` for the built item(s) instead of indexing only the staged files; emit the superseded asset names to prune. Drops the "fresh = only built items" index assumption. |
| `forge/publish/releases.py` | Serving publisher: upload new + `gh release delete-asset` the superseded version (mono-version bucket). **New** archive publisher: `{name}-v{version}` release + retention N (default 10) via `gh release delete`. |
| `forge/cli/main.py` | `mh repo build`: `--published-index-url` (omit → full build). `mh publish`: `--archive` flag + `--keep N` (default 10). |
| `.github/workflows/forge-release.yml` | Wire `FORGE_PUBLISHED_CATALOG_URL` + the published-index URL (post-cutover); publish job runs serving (prune) + archive (N=10). |

## 6. Decomposition (each a mergeable, TDD'd PR; pipeline green between)

- **SP4.7.1** — rpm serving: `merge_rpm_repo` (record new `.rpm` + `mergerepo_c
  --method nvr --omit-baseurl` over the published `repodata/`) + published-index
  fetcher + prune the superseded asset. FakeRunner tests: createrepo runs on the
  one new file, mergerepo gets both repos with the right flags, `delete-asset`
  called for the superseded version, no-published-index falls back to a full build.
- **SP4.7.2** — apt serving: `merge_apt_repo` (record new `.deb` stanza, splice
  into the published `Packages`, regen `Packages.gz` + `Release`). Tests: an
  unchanged item's stanza is carried over verbatim; the changed item keeps exactly
  one (the new) stanza; index stays mono-version.
- **SP4.7.3** — archive publisher + N=10 retention. FakeRunner tests: release
  created with the version's artifacts; exactly the 10 newest kept, older
  deleted; semver sort correct.
- **SP4.7.4** — workflow wiring: `FORGE_PUBLISHED_CATALOG_URL` set, publish job
  calls serving + archive. Gated end-to-end smoke on a real single-item bump
  proving the other 33 remain in the repo index and the bucket stays bounded.

## 7. Out of scope

- Multi-version repo serving (`dnf --showduplicates` / `dnf downgrade` via the
  repo) — explicitly rejected (§2); would require a multi-version catalog model.
- Cleanup of the 63 legacy `*-v*` releases — already a separate deferred task.
- Docker/OCI publishing — unchanged (GHCR/Docker Hub, not Releases).
