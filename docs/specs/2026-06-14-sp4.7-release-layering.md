# SP4.7 — Release layering: bounded serving + per-app archive

> Sub-spec of SP4 (release automation). Addresses the SP4.7-#1 follow-up:
> the new pipeline collapsed the legacy per-app release channel into flat
> per-target blob buckets that grow without bound. This spec splits the two
> concerns the buckets conflate — **serving** the repo vs **archiving**
> versions — and makes the serving layer truly incremental.

**Status:** design approved 2026-06-14, pending implementation plan.

---

## 1. Problem

### 1.1 What the legacy did (two parallel channels)

- **Repos (apt/yum):** packages lived physically on `gh-pages`
  (`<dist>/<arch>/*.rpm` next to `repodata/`; apt `pool/` + `dists/`).
  `createrepo`/`apt-ftparchive` indexed them in place. This is what
  `dnf`/`apt` consumed.
- **Per-app GitHub Releases** (`node_exporter-v1.11.1`, …): a *separate*
  visibility/direct-download channel, one release per app per version. Not
  consumed by the repos. Each release was small (one version's artifacts) and
  individually prunable.

### 1.2 What the new pipeline does

- **Pages** holds only metadata (rpm `repodata`, `catalog.json`, GPG keys,
  dashboards) — ~5–15 MB, effectively constant.
- **Releases** hold the blobs, keyed by **repo coordinate**:
  `rpm-<target>-<arch>/*.rpm` (rpm repodata on Pages points here via
  createrepo `--location-prefix`) and `apt-<codename>/` (the whole apt tree:
  `pool/` + `dists/`).
- **No per-app releases.**

### 1.3 The two defects

1. **Unbounded growth.** The publisher only does `gh release upload
   --clobber`. A new version has a new filename, so the old `.rpm` is never
   removed: each per-target bucket accumulates every version of every exporter
   forever. 300 bumps → 300+ assets piling into a single release, growing
   without retention. A release with thousands of assets degrades the UI/API.
2. **Serving is not actually incremental.** `build_rpm_repo` runs
   `createrepo_c` over the **physically staged** packages, which on an
   incremental run contain only the freshly-built item(s) (`rpm_groups` is fed
   by `_stage_artifacts` from `dist/` = built items only). `build_apt_repo`
   likewise rebuilds the pool from the current run's debs only. So a single-item
   run regenerates a repodata/`Packages` index listing **only that item** —
   dropping the other 33 from the index. The `FORGE_PUBLISHED_CATALOG_URL`
   merge fixes `catalog.json` but **not** the repo metadata. Today only
   `mode=all` (full rebuild) yields a complete repo.

### 1.4 Lost capability

The legacy per-app channel gave per-version visibility and manual downgrade
(`curl` the old rpm + `dnf install ./file.rpm`). The new model keeps the files
(by accident, in the flat bucket) but loses the clean per-version grouping.

---

## 2. Decisions (locked)

| Decision | Choice |
|---|---|
| Repo serves multiple versions of an item? | **No** — mono-version repo. The
repodata/`Packages` index the manifest-pinned version only (as legacy did).
Catalog model is **unchanged**. Downgrade is via the archive layer (direct
download), not via `dnf downgrade`. |
| Archive retention | **Keep the last 10 versions** per exporter (per-app
releases beyond the 10 most recent are deleted). |
| Serving layer location | **Releases** (per-target buckets), not Pages —
the current-version blob set across all targets is several GB, over the Pages
~1 GB soft limit. Pages stays metadata-only. |
| Full rebuild on every bump? | **No** — incremental strict. No re-download /
re-package of unchanged items. |

## 3. Target architecture: two layers

```
┌─ SERVING (what dnf/apt hit) — CURRENT VERSION ONLY, BOUNDED ───────────┐
│  Releases (blob CDN):                                                   │
│    rpm-el9-x86_64/   node_exporter-1.12.0…rpm  + 33 others (current)   │
│    rpm-el9-aarch64/  …                                                  │
│    apt-bookworm/     pool/ (current debs) + dists/                     │
│  Pages: rpm repodata + catalog.json + GPG keys + dashboards (~10 MB)   │
│  Invariant: exactly one version per item per coordinate.               │
│  At bump: old version of the changed item is PRUNED from the bucket.   │
└────────────────────────────────────────────────────────────────────────┘
┌─ ARCHIVE (visibility + manual downgrade) — LAST 10 VERSIONS ──────────┐
│  Per-app Releases, one per version:                                    │
│    node_exporter-v1.12.0  → its rpm (all targets) + deb (all codenames)│
│    node_exporter-v1.11.1                                               │
│    … (≤10; older auto-deleted)                                         │
│  Each release small + individually prunable. Docker stays on GHCR/Hub. │
└────────────────────────────────────────────────────────────────────────┘
```

The current version's `.rpm` exists in two places (serving bucket + its
version's archive release). Duplication is intentional and free on Releases.

---

## 4. Mechanics: durable store + delta

The **serving buckets are the durable state.** Each incremental run, per
`(target, arch)` coordinate:

1. **Fetch** the existing index state (the small `repodata`/`Packages` from
   Pages / the apt release) — not the blobs.
2. **Delta** — remove the changed item's previous version, add its new version.
   The bucket stays mono-version → bounded (one entry per item).
3. **Re-index** over the *complete* current set using incremental tooling:
   - rpm: `createrepo_c --update` reads the old repodata as a cache and only
     re-reads the new `.rpm`; unchanged entries carry forward. The old
     version's asset is removed via `gh release delete-asset`.
   - apt: regenerate `dists/Packages` over the merged set — existing `Packages`
     stanzas carried forward + the changed item's stanza substituted (apt's
     `Filename:` is pool-relative, so the index can be merged from the existing
     stanzas without re-hosting every `.deb`; exact mechanism left to the plan).
4. **Sign + push** — signed metadata clobbered onto Pages (rpm) / the apt
   release; the new blob uploaded to the bucket, the old blob deleted.

No upstream fetch, no nfpm, no re-signing of the 33 unchanged packages.

### Archive layer (independent)

For each built item: create/clobber the `{name}-v{version}` release with that
version's rpm (all targets) + deb (all codenames); then list `{name}-v*`
releases, sort by semver, and `gh release delete` everything beyond the 10 most
recent.

## 5. Code surface

| Component | Change |
|---|---|
| `forge/repo/builder.py` | `build_distribution` becomes delta-aware: takes the existing durable index state as input, applies add/remove, re-indexes incrementally. Drops the "fresh = only built items" assumption. |
| `forge/repo/rpm.py` | `build_rpm_repo`: `--update` against existing repodata; signal the old-version asset to prune (mono-version bucket). |
| `forge/repo/deb.py` | `build_apt_repo`: merge existing pool + substitute the changed deb + regenerate `dists/`. |
| `forge/publish/releases.py` | Serving publisher: `delete-asset` (old) + upload (new) — prune to current. **New** archive publisher: `{name}-v{version}` release + retention N (default 10) via `gh release delete`. |
| `forge/cli/main.py` | `mh publish`: archive flag + `--keep N` (default 10). `mh repo build`: durable-state input. |
| `.github/workflows/forge-release.yml` | Wire `FORGE_PUBLISHED_CATALOG_URL` (post-cutover); publish job runs serving (prune) + archive (N=10). |

## 6. Decomposition (each a mergeable, TDD'd PR; pipeline green between)

- **SP4.7.1** — rpm serving: `createrepo_c --update` + prune old version from
  bucket. FakeRunner tests: only the delta is indexed; `delete-asset` called for
  the superseded version.
- **SP4.7.2** — apt serving: pool delta (merge existing + substitute) +
  `dists/` regen. FakeRunner tests: pool stays mono-version; index lists all.
- **SP4.7.3** — archive publisher + N=10 retention. FakeRunner tests: release
  created with the version's artifacts; exactly the 10 newest kept, older
  deleted; semver sort correct.
- **SP4.7.4** — workflow wiring: `FORGE_PUBLISHED_CATALOG_URL` set, publish job
  calls serving + archive. Gated end-to-end smoke on a real single-item bump
  proving the other 33 remain in the repo index and the bucket stays bounded.

---

## 7. Out of scope

- Multi-version repo serving (`dnf --showduplicates` / `dnf downgrade` via the
  repo) — explicitly rejected (§2); would require a multi-version catalog model.
- Cleanup of the 63 legacy `*-v*` releases — already a separate deferred task.
- Docker/OCI publishing — unchanged (GHCR/Docker Hub, not Releases).
